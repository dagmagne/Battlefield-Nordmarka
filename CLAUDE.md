# Battlefield Nordmarka

Real-time WebGPU winter tank game: command a Norwegian Leopard 2A4NO against Russian armour (T-72B3, BMP-2) in Nordmarka. It grew out of a snow-groomer showcase (`groomerweb`), so the engine, the worlds and many names (`groom` uniforms, the grooming mask) still come from that. No engines (no Three.js/Babylon). The deliverable is **one URL** (GitHub Pages): open it on any device and play, with nothing to install. Today the build is still a single self-contained `index.html`; the owner has agreed (2026-11-23) that data may be served as separate files beside it, as long as a single-file build remains possible (see `plans/architecture.md`).

There are two worlds, chosen on the start screen (or with `?w=`):
- **Real Nordmarka** (`?w=holmenkollen` or `?w=frogner`; same world, two start points). A 4×4 km window (origin 59.9753 N, 10.6800 E, x = east, z = south) with about 3×3 km drivable: Holmenkollbakken, Midtstubakken, Frognerseteren, Tryvannstårnet, Holmenkollen kapell, Øvresetertjern, real ski trails, about 3800 houses, the plowed roads you navigate by (Holmenkollveien down to a few hundred metres below the arena, Voksenkollveien, Øvreseterveien, Tryvannsveien) and 45 parking lots. The macro shape comes from map data; everything else is procedural.
- **Fantasi** (`?w=fantasi`): the original fully procedural world (three mountains, lakes, creek, dam, bridge) in `src/fantasy.js`. Free roam only: no enemy waves.

Scripted runs with `?nohint` and no `?w` default to Frognerseteren.

**Start points (`START` in `world.js`):** the tank starts on a plowed car park by a road, facing up the road: Frognerseteren = the car park at the junction of Tryvannsveien and Holmenkollveien by the station (-317, -314), Holmenkollen = the car park on Holmenkollveien east of the arena (-310, 1179). The groomer's start (a point on a ski trail, facing along the trail) is still computed, because `W.startI` on `trails[0]` drives the scripted runs (`auto`, `perf.mjs`, `scenes.mjs`). Missions from Frognerseteren start on the road at that junction (`FROG` in `missions.js`, snapped to the road and turned towards the first objective); `arena` starts in the arena, `night` at the Tryvann car park. The column mission's route runs through the junction, so a vehicle with a goal and `hold: 0` no longer halts within 70 m of the tank: it pushes past.

**Game modes** (start screen: mode, then mission / start point / world; `#pick` holds the groups `#pg0`–`#pg3`): **Missions** (six scripted fights, `?m=<id>`), **Defence** (the six waves, `?w=holmenkollen|frogner`) and **Free roam** (`?peace`; the fantasy world is always free roam). The choice on the start screen wins over a stored peace-mode setting.

## Priorities (in order)
1. **Visual quality.** This is a desktop showcase.
2. **Smooth frame pacing** on every target platform (see below). The quality tiers, the Trees setting and DRS are the tools for weaker hardware; there is no single reference machine any more.
3. **Small bundle.** Currently about 4389 kB (about 3081 kB gzip; the Norwegian translation about 34 kB, game modes and missions about 20 kB, the camouflage net about 4 kB; the vehicle and metro-train rebuild added about 88 kB; functional bridges about 13 kB (milestone 2 about 3 kB), the road network and Holmenkollbanen before that about 120 kB; the lidar map data added about 1290 kB: `world.bin` went from 347 to 1308 kB, of which the 4 m height grid 647 kB, the arena inset 111 kB, the Tryvann inset 40 kB, canopy cover 347 kB; the arena, landmark and ski-jump builders about 30 kB; before that 2773 kB with controller vibration about 3.5 kB; phases 1–4 (drones, mines, enemy air, light vehicles) added about 36 kB, enemy artillery about 3 kB, infantry logic about 19 kB; the music added about 1.6 MB and the title image about 316 kB, the recorded sound loops about 110 kB, procedural sound about 10 kB and destructible buildings about 15 kB). The owner has said bundle size is not a strict limit for map realism. Report the size after changes.

**Target platforms: cross-platform.** Windows PC, Mac, phones and iPad, in current Chrome, Edge and Safari. The owner works mainly on a Windows laptop with an NVIDIA card (Edge / Chrome); the Mac-only wording and the M2 Max numbers further down come from the groomer project and are historical. The touch UI (`?touch`) is a first-class part of the game and has to be kept working: anything added for keyboard and mouse needs a touch control too. Check the layout with `tools/cshot.mjs ... --touch --w 852 --h 393` (phone, landscape) and an iPad-sized viewport.

What has actually been run where, so far: Windows + NVIDIA (found the `pow` NaN line, about 50 fps with everything on high), Windows + integrated Intel `gen-12lp` (23 fps on the low tier), iPhone (played, no artefacts reported). Linux desktop + GTX 1060 6GB (driver 580, Chrome 157): the GPU tools below run here on the real card, so frame and GPU time can now be measured by the agent (see the baseline under Performance discipline). Not run in this round: Mac, iPad, Android. Nothing here can listen to sound: that needs the owner's ears.

Fullscreen: a FULL button in the touch top bar (`#bFs`, `ui.js`) calls `requestFullscreen` and on Android locks the screen to landscape; it is only shown where the browser supports page fullscreen (Android, iPad), because iPhone Safari does not. On iPhone the way to a full screen is Add to Home Screen (`apple-mobile-web-app-capable` is set). Known gaps on touch (no button yet, keyboard only): the thermal sight (V), sound on/off (M; the menu row works), restart (R; the end card's button works), snowfall (N; menu). The settings menu has grown (a Music row was added) and scrolls on a phone; its Close button is below the fold at 393 px height.

## Hard rules
- WebGPU only. No external texture, model or audio files. The exceptions are the map data blob `src/data/world.bin`, the recorded sound loops in `src/data/snd/*.mp3`, the music `src/data/music.mp3` and the title-screen image `src/data/title.webp` (all supplied by the owner), which the build embeds as base64 (they may become separate files on the same site, see `plans/architecture.md`); the existing meshes, textures and detail are procedural. **Imported (freely licensed) models are allowed for new units** (owner's decision, 2026-11-23): converted at build time, no run-time loader library; the toolchain is documented in `docs/imported-models.md` and the working FPV-drone pilot is on the branch `claude/fpv-model` (not merged yet). Record the source and licence of every imported model.
- **No per-frame JS allocations** in the frame loop. Use preallocated typed arrays and no closures, arrays or objects per frame. Allocating on rare events (toasts, key presses) is fine.
- If WebGPU is unavailable, show a friendly message instead of a blank page.
- Never leave the build broken. Rebuild after every meaningful change and run `npm run check` (the browserless checks; CI runs the same on every push) before committing.
- Commit after each milestone or fix, with a short imperative message. Commit only when it works.

## Build and run
- Source lives in `src/` (`*.js`, `*.wgsl`, `shell.html`). `node build.mjs` bundles it with esbuild and a WGSL minifier into `index.html`, then prints the size. `node build.mjs --dev` skips minification.
- Serve with `npm run serve` (`python3 -m http.server 8080`) and open http://localhost:8080. The server is usually already running, so check with `lsof -iTCP:8080` before starting one.
- **Split build (`node build.mjs --split`, step 2 of `plans/architecture.md`):** writes `dist/` instead: `index.html` (shell + code, about 682 kB, 301 kB gzip) with `world.bin`, `music.mp3` and `title.webp` as separate files named by content hash, and `sw.js` (from `src/sw.js`: the page network-first, the data files cache-first, byte ranges cut from the cache for the music element; its scope is its own directory). `src/asset.js` tells the two forms apart (base64 text or a `./` URL): `assetBytes`, `assetUrl`; `preloadWorld()` starts the map download while the start screen is up; the sound loops stay embedded. A failed map download shows the `#err` card. **The single-file build is still the default and what every tool loads; GitHub Pages serves it at the root and the split build under `/next/` for trial.** The owner has tried `/next/` on an iPhone (2026-11-23): it starts, the music plays, and it starts from the home screen in flight mode; iPad, Mac Safari and Android are untried. Making it the root is the owner's call. `tools/splittest.mjs` (headless, software WebGPU, serve the repository root): the split build fetches the files, reaches `__ready`, the worker takes control, and an offline reload still starts, music included.
- Don't edit `index.html` by hand. It is a build output and is **not in git** (ignored): a fresh checkout needs `npm ci && node build.mjs` before anything can be served. GitHub Pages builds it from source (`.github/workflows/pages.yml`: checks, build, deploy on a push to `main`); `.github/workflows/ci.yml` runs `npm run check` and the build on every other branch and writes the bundle sizes to the job summary.

## Architecture: where to read
`main.js` is the orchestrator (quality tiers, pipelines, the frame loop, cameras, vehicle physics, fire control); `combat.js` holds the fighting; `world.js` builds the real world from `src/data/world.bin`. The detailed notes per system live in `docs/dev/`. **Read the file for a system before changing it, and update it in the same commit** (constants, measured numbers, what was tried and why it was dropped). Keep this file short: new system notes go in `docs/dev/`, not here.

- `docs/dev/vehicles.md` — **Vehicles and models.** The Leopard, the running gear and track loops, T-72, BMP, Tigr, BTR, buggy, motorcycle and their crews, vehicle materials, MX3000 metro units.
- `docs/dev/combat.md` — **Combat, driving and the game loop.** `combat.js`: shells, damage, enemy AI and roles, waves, reload, enemy detection and gunnery, the tank's driving and fire control.
- `docs/dev/drones.md` — **Drones and enemy air.** The player's FPV, bomber and recon drones (flight, cameras, video look, OSD is under ui.md), enemy FPV, Lancet and Orlan, the hatch MG, cope cages.
- `docs/dev/mines-artillery.md` — **Mines and artillery.** Minefields and rocket-laid mines, enemy artillery (`arty.js`), own fire missions (`support.js`).
- `docs/dev/infantry.md` — **Infantry.** Soldier model, poses and rendering (`soldier.js`), infantry logic (`infantry.js`): RPG and ATGM teams, dismounts.
- `docs/dev/missions.md` — **Missions and the camouflage net.** `missions.js` (stages, script API, the six missions, cards) and the camouflage net (`net.js`).
- `docs/dev/rendering.md` — **Rendering.** `main.js` as orchestrator, HDR pipeline, terrain clipmap, snow mask, trees and tree felling, shadows, particles, thermal sight.
- `docs/dev/world.md` — **The world.** `world.js`, roads and parking, props, destructible buildings, lidar in the game (ski jumps, arena, landmarks), Holmenkollbanen, the fantasy world, the playable area.

- `docs/dev/audio.md` — **Sound, music and vibration.** `audio.js` (recorded loops and procedural sound), `music.js` and the title screen, controller vibration (`haptics.js`).

## Verification workflow (always do this, don't just reason about the code)
- `npm run check` runs the browserless checks and the type check (`tsc -p .`, JSDoc types, `src/types.d.ts` for ambient declarations); CI runs it on every push. A new property on a shared object goes into the object literal where it is created, or the type check fails.
- Behaviour is tested by scripted fights in a real browser through the test hooks (`__sim` steps the logic without rendering); visual changes are verified with renders from fixed views. The tools, their options and the hooks are in `docs/dev/testing.md`. The GPU tools need a machine with a graphics card; in a cloud container only the headless ones (`cshot`, `splittest`) run.
- Screenshots go in `shots/<topic>/`. Look at them yourself with Read before you claim something looks right.

### Visual critic gate
For larger visual milestones, run a **critic subagent that sees only the renders** (no code, no intent). Have it grade issues as MAJOR/MODERATE/MINOR, then fix and re-render until nothing above MINOR remains. The original gate passed in round 6 (history: 5 MAJOR → 8 MODERATE → 4 → 3 → 1 → MINOR only). The final review is in `critic-final.md`.

### Performance discipline
- Measure GPU time with timestamp queries, not just frame time. Compare before and after with an **A/B under identical conditions** (stash, build, measure, pop).
- Other apps on the machine (browser, IDE, WindowServer) skew absolute numbers a lot. Report the load you saw, and don't treat a loaded-machine number as the baseline. The idle baseline on high/native was frame avg 14.2 ms / p99 18.3 ms and GPU avg 12.9 ms / p99 15.4 ms. (That baseline is the groomer on an M2 Max.)
- **Who runs what (owner's rule, 2026-11-20):** mechanical runs — the behaviour suites (`lighttest`, `wavetest`, `bridgetest`, ...) and performance measurement (`vehgpu.mjs`, `perf.mjs`, `treegpu.mjs` A/B) — go in a background script from the main session or to a cheaper subagent (Sonnet) that only runs the given commands and reports PASS/FAIL lines, numbers and `uptime`; it does not diagnose or fix. Interpreting a failure (known noise: `roadtest` near its limit, rare `[pageerror] undefined` bursts, `wavetest` stuck counts), diagnosis and judging renders stay on the main model. Subagents that build something run only the one test they need to know the game still works, with a capped number of render rounds (three was enough for the BTR and T-72); the full suite and the perf A/B are run once on the combined build.
- The baseline numbers (GTX 1060) are in `docs/dev/testing.md`. Use `drs=0` for A/B comparisons.

## How the work was done (process to keep following)
1. **The first prompt was a full spec**: the world, groomer, grooming mask, controls, quality tiers and DRS, the verification plan and a "done when the critic gate passes" criterion. Write a working `index.html` early, then iterate in milestones (terrain, then trees, then groomer and mask, then lighting and post, then UI and perf). Overwrite `index.html` and commit after each one.
2. **Every visual change is verified with renders**: the fixed poses, drive frames and video where motion matters. Analyse problems quantitatively when possible (mean colour per LOD, frame-time stats) instead of eyeballing.
3. **Follow-up requests from the user are in Norwegian, and you answer in Norwegian.** (The in-game UI is English in the code; Norwegian is a translation layer, `lang.js`.) The pattern is: analyse the root cause with measurements, explain what was wrong, fix it, verify with renders and perf, commit, and report briefly with honest caveats (what wasn't verified, and measurement noise).
4. **Examples of follow-ups:**
   - The tree LOD "pop" (heavy snow at a distance, little up close) was fixed with consistent snow extent on all LODs, shading for the far LODs, and a two-phase cross-fade.
   - Turbo mode (driving fast, drifting and jumping) added kickers on the lake and ballistic physics. It was removed again when the groomer became a tank; only the ballistic crest physics survives.
   - The tank conversion: Leopard model, driving and fire control, weapons and effects, Russian enemies with AI, waves and HUD, in that order, one commit per milestone.
   - Real Nordmarka (phase 1): map data pipeline, real terrain, lakes, trails, houses and landmarks, then a start screen to choose between the real world (two start points) and the fantasy world. Phase 2 (not started) is streaming trees and a larger world north to Kikut.
5. When a usage limit interrupts the work, resume where it stopped without redoing finished work.

## Lessons / gotchas (general; system-specific ones are in `docs/dev/`)
- Blanket renames in WGSL can corrupt identifiers (for example `duv.x` became `dux`). Grep after any mechanical edit.
- Work queued for the renderer during logic-only steps (`__sim`) must survive until a frame is drawn: `blastN` is cleared by the renderer, not by `update`.
- Never append a `//` comment in the middle of a one-line statement chain (this also holds for Python and for JS inside a test's template string, which `commentlint` does not see; the bridge work hit all three): it silently swallows the statements after it (this removed the whole road mask once, and bit the drone, mine and tree work repeatedly). `build.mjs` now runs `tools/commentlint.mjs` first and stops on a trailing comment that looks like it hides code.
- Spotlight indexing (`mds`) and other apps can push GPU times to 100+ ms. Check `uptime` before trusting a perf number.
- Other sessions' dev servers may already hold ports near 8080–8095; a `python3 -m http.server` that cannot bind fails silently in the background, and the tools then talk to someone else's checkout. Check with `lsof -iTCP:<port>` and `readlink /proc/<pid>/cwd`.
- Clamp the base of every `pow` in WGSL: a base a rounding error below zero is NaN on D3D12 (the NVIDIA pixel line; the full story is in `docs/dev/rendering.md`).
- `genWorld` in `world.js` is close to the size where V8 stops optimising a function: put new world-generation steps in module-level functions and check the load time (`docs/dev/world.md`).
- Anything that moves must test bridge slabs with `W.br.seg` before using `groundAt` (`docs/dev/bridges.md`).
