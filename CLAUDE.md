# Battlefield Nordmarka

Real-time WebGPU winter tank game: command a Norwegian Leopard 2A4NO against Russian armour (T-72B3, BMP-2) in Nordmarka. It grew out of a snow-groomer showcase (`groomerweb`), so the engine, the worlds and many names (`groom` uniforms, the grooming mask) still come from that. No engines (no Three.js/Babylon). The deliverable is a single self-contained `index.html`.

There are two worlds, chosen on the start screen (or with `?w=`):
- **Real Nordmarka** (`?w=holmenkollen` or `?w=frogner`; same world, two start points). A 4×4 km window (origin 59.9753 N, 10.6800 E, x = east, z = south) with about 3×3 km drivable: Holmenkollbakken, Midtstubakken, Frognerseteren, Tryvannstårnet, Holmenkollen kapell, Øvresetertjern, real ski trails, about 3800 houses, the plowed roads you navigate by (Holmenkollveien down to a few hundred metres below the arena, Voksenkollveien, Øvreseterveien, Tryvannsveien) and 45 parking lots. The macro shape comes from map data; everything else is procedural.
- **Fantasi** (`?w=fantasi`): the original fully procedural world (three mountains, lakes, creek, dam, bridge) in `src/fantasy.js`. Free roam only: no enemy waves.

Scripted runs with `?nohint` and no `?w` default to Frognerseteren.

**Game modes** (start screen: mode, then mission / start point / world; `#pick` holds the groups `#pg0`–`#pg3`): **Missions** (six scripted fights, `?m=<id>`), **Defence** (the six waves, `?w=holmenkollen|frogner`) and **Free roam** (`?peace`; the fantasy world is always free roam). The choice on the start screen wins over a stored peace-mode setting.

## Priorities (in order)
1. **Visual quality.** This is a desktop showcase.
2. **Smooth frame pacing** on every target platform (see below). The quality tiers, the Trees setting and DRS are the tools for weaker hardware; there is no single reference machine any more.
3. **Small bundle.** Currently about 4347 kB (about 3067 kB gzip; game modes and missions about 19 kB; the vehicle and metro-train rebuild added about 88 kB; functional bridges about 13 kB (milestone 2 about 3 kB), the road network and Holmenkollbanen before that about 120 kB; the lidar map data added about 1290 kB: `world.bin` went from 347 to 1308 kB, of which the 4 m height grid 647 kB, the arena inset 111 kB, the Tryvann inset 40 kB, canopy cover 347 kB; the arena, landmark and ski-jump builders about 30 kB; before that 2773 kB with controller vibration about 3.5 kB; phases 1–4 (drones, mines, enemy air, light vehicles) added about 36 kB, enemy artillery about 3 kB, infantry logic about 19 kB; the music added about 1.6 MB and the title image about 316 kB, the recorded sound loops about 110 kB, procedural sound about 10 kB and destructible buildings about 15 kB). The owner has said bundle size is not a strict limit for map realism. Report the size after changes.

**Target platforms: cross-platform.** Windows PC, Mac, phones and iPad, in current Chrome, Edge and Safari. The owner works mainly on a Windows laptop with an NVIDIA card (Edge / Chrome); the Mac-only wording and the M2 Max numbers further down come from the groomer project and are historical. The touch UI (`?touch`) is a first-class part of the game and has to be kept working: anything added for keyboard and mouse needs a touch control too. Check the layout with `tools/cshot.mjs ... --touch --w 852 --h 393` (phone, landscape) and an iPad-sized viewport.

What has actually been run where, so far: Windows + NVIDIA (found the `pow` NaN line, about 50 fps with everything on high), Windows + integrated Intel `gen-12lp` (23 fps on the low tier), iPhone (played, no artefacts reported). Linux desktop + GTX 1060 6GB (driver 580, Chrome 157): the GPU tools below run here on the real card, so frame and GPU time can now be measured by the agent (see the baseline under Performance discipline). Not run in this round: Mac, iPad, Android. Nothing here can listen to sound: that needs the owner's ears.

Fullscreen: a FULL button in the touch top bar (`#bFs`, `ui.js`) calls `requestFullscreen` and on Android locks the screen to landscape; it is only shown where the browser supports page fullscreen (Android, iPad), because iPhone Safari does not. On iPhone the way to a full screen is Add to Home Screen (`apple-mobile-web-app-capable` is set). Known gaps on touch (no button yet, keyboard only): the thermal sight (V), sound on/off (M; the menu row works), restart (R; the end card's button works), snowfall (N; menu). The settings menu has grown (a Music row was added) and scrolls on a phone; its Close button is below the fold at 393 px height.

## Hard rules
- WebGPU only. No external texture, model or audio files. The exceptions are the map data blob `src/data/world.bin`, the recorded sound loops in `src/data/snd/*.mp3`, the music `src/data/music.mp3` and the title-screen image `src/data/title.webp` (all supplied by the owner), which the build embeds as base64; all meshes, textures and detail are still procedural. Imported (freely licensed) models have been piloted but are **parked**: the toolchain is documented in `docs/imported-models.md` and the working FPV-drone pilot is on the branch `claude/fpv-model`; adopting it needs the owner's go-ahead and an exception here.
- **No per-frame JS allocations** in the frame loop. Use preallocated typed arrays and no closures, arrays or objects per frame. Allocating on rare events (toasts, key presses) is fine.
- If WebGPU is unavailable, show a friendly message instead of a blank page.
- Never leave `index.html` broken. Rebuild after every meaningful change.
- Commit after each milestone or fix, with a short imperative message. Commit only when it works.

## Build and run
- Source lives in `src/` (`*.js`, `*.wgsl`, `shell.html`). `node build.mjs` bundles it with esbuild and a WGSL minifier into `index.html`, then prints the size. `node build.mjs --dev` skips minification.
- Serve with `npm run serve` (`python3 -m http.server 8080`) and open http://localhost:8080. The server is usually already running, so check with `lsof -iTCP:8080` before starting one.
- Don't edit `index.html` by hand. It is a build output.

## Architecture overview
- **`main.js`** is the orchestrator: quality tiers (low/medium/high/ultra, auto-selected plus a manual override in the menu), pipelines, the frame loop, cameras, vehicle physics (`simulate`), fire control (`updateAim`), stamps, particles, dynamic resolution (DRS) and the perf harness.
- **`leopard.js`, `gear.js`:** the player's Leopard 2A4NO (`buildLeopard`, `LEO`; about 25 000 triangles: welded turret shell from a plan (`shell`, 3.2 m wide, roof 2.46 m) with the EMES 15 seated in a notch in the right cheek, PERI R17, cupola, MG3 on a skate rail, discharger cups, bustle basket, wedge mantlet set back between the cheeks, skirts (the first heavy module cut away over the idler), engine deck, rear louvre band, Rh-120 with sleeve and fume extractor) and the shared running gear (`runningGear(b, type, colour, hi)`). **Track loops:** `GEAR` holds per tracked vehicle (0 Leopard, 1 T-72, 2 BMP) the road wheels, idler, sprocket and link thickness; `trackLoop` turns that into the convex hull of four circles (4 straight runs, 4 arcs: ground run, rise to the sprocket, return run, fall from the raised idler), `loopAt` evaluates it, and `TRACK_WGSL` is the same table as WGSL constants (`TRKL`, `TRKT`) that `main.js` puts in front of `objdeform.wgsl`, so the animated link bars (`MAT.bar`, pos = (x, along, outward), uv = (loop position, side), last vertex float = vehicle type) follow the same path as the belt mesh. The road wheels stand on the links (link outer face = ground line, y 0). The whole running gear is part 3: `tankParts` writes a fourth matrix without the hull's suspension rocking (`dp`, `dr`), so the links stay on the ground when the hull squats (wheeled vehicles overwrite part 3 with their first axle). `TRK` only holds the track centre line and width now (stamps, physics). Mesh helpers: `face`, `cbox` (chamfered box), `plate`, `lathe` (with `uvr` it writes polar uv for `MAT.wheel`: bolt ring, dish dirt, matt black tyre beyond 0.76 of the radius), `pipe`, `fixWinding` (helpers only guarantee normals; `fixWinding` makes the winding follow them). `MAT.camo` paints whitewash as strokes: two sets of capsules on jittered grids (broad swabs, a sparser set crossing them), each with its own angle, length and width, ragged edges and bristle streaks, 0.6 coverage at the front falling to 0.42 at the sooty rear; every face is painted in its own plane, chosen by a hard switch on the part-space normal (`nlp`, from derivatives of `lp` taken at the top of `fs` and weighted so a 45 degree chamfer does not flicker between two planes); the vertex green channel seeds the strokes (`tint` in `leopard.js`; keep `fract(g * 9000 + 0.37)` away from an integer or the seed flips per pixel). Vehicle materials (20, 21, 8, 14) get a strong fill term for light bounced off the snow (one line after the main lighting sum in `object.wgsl`): without it the shaded side was a black silhouette (shadowed olive 0.005 displayed luminance, now about 0.03-0.045). Dark parts need a very low specular (0.004-0.012): with more, the sun term turns albedo 0.03 nearly white. The turret bustle and its basket sweep the engine deck at 1.81 m, so nothing on the deck may stand higher. `node tools/leocheck.mjs` (no GPU) prints triangle counts, bounds per part, the Leopard's proportions and the loop figures, and fails on NaN or a winding that disagrees with the normals; `tools/vehshots.mjs` renders the look-check views, including the Leopard on bare ice and a drive / pivot / reverse check of the links (`--q therm=1` adds query parameters).
- **`tank.js`:** the other tracked vehicles (`buildT72`, `buildBMP`; it re-exports `buildLeopard`) and `tankParts`, which writes the part matrices (0 hull, 1 turret, 2 gun). The tracked vehicles share one running gear (`gear.js`). The per-vehicle constants (`LEO`, `T72`, `BMP`) hold the turret ring, trunnion, muzzle and hit-box sizes. `tankParts` uses shared scratch matrices, so `main.js` copies the player's into `hullM` / `turM` / `gunM` before the enemies are updated.
- **`combat.js`:** everything about fighting, preallocated in `initCombat`: the shell pool (APFSDS, HEAT-MP, HE, coax MG, enemy 125 mm and 30 mm, smoke grenades; shell types 0–12 are listed above `TRACE`, 12 being the RPG rocket of the infantry) with ballistic flight and sub-stepped hits against terrain, buildings (`C.bld.at`, real roof height), circle colliders (`collAt` grid) and vehicle hit boxes; building damage and collapse effects (`bldHit`, `bldState`: dust cloud, debris chunks, a few seconds of fire for HE and the drone, scorch, shake, `C.sfx('collapse')`); damage by zone and facing; explosions, muzzle blast, tracers and flashes (`fx` glow sprites plus the `l2` flash light); smoke clouds that block line of sight; enemy AI (follow trails towards the player, pushed out of buildings and colliders through `C.solid`, line of sight through terrain, intact buildings, canopy raster and smoke, lead and aim error, reload); waves, resupply, score, the minimap and the HUD pills.
- **Minimap (`minimap.js`):** the whole world is rendered once at load into a hidden canvas at the minimap's own scale (464 backing px for 2400 m, shown at 232 CSS px on desktop; touch 150 px, 104 or 96 px on a phone, where `drawMap` scales the markers up so they keep their size): relief shading, forest, water, bog, parking lots, dashed ski trails, roads (`W.roads`, wide ones brighter), buildings and the playable border. `drawMap` in `combat.js` (every 0.2 s) blits the window around the tank or drone at an integer offset and draws the markers on top. **Enemies appear only once seen** (`e.spotT` s left as a fresh contact, `e.seen`, last known `e.lx/lz`, `e.lostT`): the crew sees what is inside ±0.75 rad of the sight heading or within 180 m, on the enemy's own line-of-sight value (`e.los`, the same line reversed, > 0.2), out to 1600 m by day and less at night without the thermal sight (6 s); a muzzle flash within 2500 m (8 s); a hit (10 s); any drone's camera cone (±44°, `losVis` > 0.15, staggered every 0.3 s; FPV 800 m / 20 s, bomber 900 m / 25 s, recon 1500 m / 40 s). Fresh contacts are solid; a lost one is a hollow marker at the last known position that fades over 40 s (`LOST_T`); wrecks stay grey. The wave announcement still gives direction and range. Building damage repaints that building through `B.onState` (also on `restore`). **Large map (Tab, or a click/tap on the minimap; another closes it):** `G.bigMap()` builds a second, sharper copy of the base map on first use (`initMinimap(..., k)` with k ≤ 0.6 px/m; line widths scale with k; `B.onState` chains so both copies repaint damaged buildings) and draws the playable area plus 120 m into `#bmap` every 0.25 s with the same `markers()` as the minimap (500 m ring round the tank, scale bar); `markers(..., u)` scales every marker size and line width, u = CSS size / 380 clamped 1.2–2.6 on the big map, and large markers get a dark casing on the mine crosses. `tools/mapshot.mjs outdir [--touch --w --h]` stages every marker kind and saves the HUD, minimap, big map and a crop.
- **Drones (X launches, Z / TYPE / L3 picks the type; `DTYPE` in `combat.js`, stock `G.dn`, selection `G.dsel`, `D.type`):** FPV (5), bomber `BOMB` (2) and recon `RECON` (2). Battery times are compressed for the 3 km map (real ones run 10–40 min): FPV 2 min, bomber 4, recon 6 (raised from 75/120/180 s). The HUD pill reads `FPV 5` on the tank and `BOMB ×3 · 95 s` in flight; the touch DRONE button names the selected type and the in-flight action button reads BOOM, DROP or is hidden (recon). Bomber and recon fly level on the heading (WASD), hold their height (Space/Shift; they climb to 30 m / 110 m after launch until you touch the height), and the camera is a gimbal under the airframe (`main.js`, drone mesh not drawn in its own view) that tilts down to vertical. **Bomber:** 14 m/s, 240 s, 3 VOG grenades per sortie (LMB, 0.7 s apart): shell type 7 falls with the normal shell ballistics; `predictDrop` marches the same parabola (ground, vehicles, roofs, refined by bisection) and the impact point is drawn as the gun-marker ring (`R.dropSx/Sy`, green when a grenade is ready). Damage from above: T-72 turret roof 50, engine deck (hull, local z > 0.9) 85 and immobilised, elsewhere 30; BMP 110; buildings 25; small splash. Landing on the tank (within 4.5 m, below hull + 4.5 m, under 5 m/s, after it has been 15 m away) puts the drone back in stock with fresh grenades. **Recon:** 18 m/s, 360 s, 2200 m radio, quiet (rotor gain 0.14 vs 0.4), unarmed; it spots for the map and can land back too. Crashes lose the bomber or recon drone without a warhead blast. **Recon autopilot:** X with the recon up does not cut the link: `D.auto` hands it to an autopilot that circles 80 m round the spot where it was left at its height, the camera sweeping round and down (so `droneScan` keeps spotting), until the battery is flat; you are back in the tank (the main gun works) and X takes the drone back. **FPV:** `updateDrone` flies it with the free-fly inputs (mouse turns it, WASD, Space/Shift up/down, 26 m/s, 120 s battery, 1500 m radio range) while the camera sits rigidly just behind it (a lagging follow jitters at that speed when the frame time varies) and the minimap centres on it. After a detonation the camera pulls back and watches the blast for 4.5 s (`D.hold`; LMB or X skips) before returning to the tank. LMB, a crash, a building or touching a vehicle detonates the shaped charge (kills a T-72 within about 3 m); X again cuts the link and the drone is lost. The tank stands still and can be hit meanwhile; enemies do not shoot at the drone. The model and `droneParts` (airframe plus four rotor parts) are in `tank.js`.
- **Light and wheeled vehicles (phase 4):** `ETYPE` now has six types (`T72T BMPT TIGRT BTRT BUGT MOTOT` = 0–5): T-72B3, BMP-2, Tigr-M with a Kornet (`buildTigr`), BTR-82A (`buildBTR`), an assault buggy with a PKM (`buildBuggy`) and a motorcycle team (`buildMoto`); `MAXE` = 14. Each type carries its own `K` (in `tank.js`) with hit-box half-extents `bx`/`bz`, a collision circle `cr` at ±`cs`, and for wheeled ones `wr` and axle positions `ax`: `wheelParts` writes one rolling part per axle (parts 3+, both wheels on it), after `tankParts`. Per type: `mgd` (damage per coax/hatch MG round: BTR 0.15, Tigr 0.5, buggy 6, bike 8, BMP 3), `turn` (yaw rate; fast wheeled vehicles need more to hold an 8 m route point), `score`, `sfx`, muzzle size, spread and minimap marker (`map`: T-72 circle, BMP/BTR square, Tigr yellow diamond, buggy/bike dot). The light ones have no smoke dischargers and a short `hold` (they rush in). Enemy engine pitch per type in `audio.js` (`ERATE`). **Kornet** (shell 8): 250 m/s, life 10 s; `guide()` keeps it on the tank (pure pursuit at 2.2/s, the motor cancels gravity) while the launcher still sees the tank (`losVis`, every 4th step), so smoke or cover cuts it, and it then veers 0.06–0.13 rad off its line; a smoke-grey trail; 38/50/62 hull by facing; launch toast and the HUD arrow (missiles first). **Enemy MG** (shell 9): 0.3 a hit on the Leopard. Scenarios: **Motorised raid** (3–5 buggies and bikes down the roads, a BTR, a Tigr on overwatch, a T-72 later from wave 4) and **ATGM ambush** (two Tigrs on overwatch, a BTR or BMP screen, two T-72s flanking later); the shuffled bag now holds six scenarios, and the BMP raid sometimes sends BTRs. **Roads and trails (`ETYPE.road`):** the wheeled ones (Tigr, BTR, buggy, bike) are road-bound (2) and the BMP prefers roads (1); a plowed road and a groomed ski trail count the same for them. They spawn on one (never where canopy > 90), `findRoute` looks for a road or trail up to 240 m off before driving cross-country, off a route `forestDir` bends their heading by up to ±1 rad towards the least canopy 20–45 m ahead (every 0.5 s), and their overwatch, scoot and escape spots need canopy < 45 (`canLim`). `tools/roadtest.mjs` measures it per type (Motorised raid, BMP raid, ATGM ambush).
- **Tigr and BTR (`src/wheeled.js`), shared helpers (`src/vehutil.js`):** `buildTigr` (about 12 600 triangles: tub with real wheel wells, Tigr-M nose with a low wide louvred grille and round lamps outboard, raked two-pane windscreen in bolted frames, tumblehome, underbody with frame, differentials and wishbones, Kornet mount with sight and two 1.3 m containers; `TIGR.wr` is 0.54) and the shared `tyre()` (lathed carcass, lugs, rim, nuts; optional ninth parameter `{ nuts, lugs, ctis, seg }`); `buildBTR` (about 15 950 triangles, tyres at `seg: 16`): a BTR-82A as a tub between four trapezoid wheel arches with inclined lower side plates (`sill`), lofted bow and stern, sloped upper sides, glacis with the folded trim vane, two windscreens with raised shutters, two-leaf side doors between axles 2 and 3, firing ports and vision blocks, silencers on the rear upper sides, engine-deck louvres, water-jet cover, and the low BPPU cone turret with the 2A72 in an external cradle (bore 0.13 m above the trunnion), PKTM, sight box, searchlight and smoke dischargers. Russian paint is `MAT.rus` 21: dark matt olive, streaks, slush low down, crisp-edged snow pads on upward faces; a vertex with `uv.x = -9` takes no snow (warm plates). Vehicle paint, links and wheels (materials 20, 21, 8, 14) get a snow-bounce fill light in `object.wgsl` (stronger than physical, an art fix for black shadow sides).
- **MX3000 metro units (`mxCar` and the `mx*` helpers in `props.js`):** lofted shell with tumblehome and rounded roof, flush rounded-trapezoid cab screen, three plug doors a side, bellows, roof units under a snow blanket, underfloor boxes, bogies with collector shoes on the conductor-rail side (`t.s3`); about 16 000 triangles per unit. `MAT.tglass` 31 is tinted glass over a ray-cast interior (seats, poles, far windows; `col.b = 1` = cab glass with sky reflection), `MAT.coach` 32 the satin body paint that holds its albedo back where it faces the sun (it clipped to white otherwise). `platFit()` in `world.js` fits every platform top to its track's rail head + 1.05 m as a sloping plane 8 cm off the car side (level boarding; tops moved up to +0.49 m against lidar; the collision record is stepped boxes).
- **T-72B3 (`buildT72` in `tank.js`):** about 17 400 triangles (18 500 with the cope cage, `vehshots --cage`): one smooth dome turret with eight Kontakt-5 wedges, Sosna-U box, Luna, cupola with NSVT, Tucha tubes, glacis ERA, fender bins and fuel cells, skirts with ERA on the front third, log, fuel drums, snorkel. Its road wheels are still evenly spaced (`runningGear` spaces them from n, z0, z1).
- **Motorcycle pillion gunner:** pelvis and legs in part 0, torso in part 1, head, arms and AK in part 2; `MOTO.tz` 0.64 / `gy` 1.54 / `gz` 0.59 / `mz` -0.3 put the pivot at his spine and the fire point on the muzzle. `MOTO.ya` gives the shown yaw arcs (34°–149° left, 34°–97° right): `visYaw()` in `combat.js` keeps a per-enemy shown yaw `e.vy` so he never swings through the driver (the shots still follow the true `turYaw`), passed to `tankParts(out, t, K, yaw)`. Any older sentence below about empty parts 1/2 or a fixed 40° pose is superseded.
- **Buggy and motorcycle models (`src/bikes.js`):** `buildBuggy` (tube space frame with a ring in the main hoop, wishbones and coil-overs, rear flat four with one transverse silencer, bucket seats, spare wheel on the rear stays, narrower front than rear tyres; about 17.5k triangles) and `buildMoto` (enduro: raked telescopic fork with gaiters, wire-spoked knobbly wheels in the x = 0 plane, tube frame, finned single, high exhaust, rack with a roll and two canvas panniers; about 10.3k triangles). Helpers there: `tube` / `pipe` (swept tubes, filleted corners), `lathe` (revolution about x; a doubled profile point is a hard edge), `plate`, `beam`, `knob`, `band`, `xform`, `snow` (a `MAT.snow` pillow: the vehicle materials take no settled snow in the shader), `lamp`. **The riders are the infantry model** (`buildSoldier(0, 8)`: the second argument is the segment count round the limbs) posed once at load and baked in: `pose(...)` fills the soldier pose parameters in vehicle space (`RIG` and `S.place` are exported from `soldier.js` for this), `bakeRider(b, { rifle, pack, toe, up, straps })` solves it with the soldier IK, levels the soles (the model's ankle is rigid), drops the pack where a seat back is, tones the overall down to a warm grey-white (about 0.62) and darkens seat, inner thighs, knees, cuffs and undersides in the vertex colours (the object shader has no occlusion, so white cloth in shade looked self-lit), adds shoulder caps that run into the torso, harness straps and goggles. In the thermal sight `object.wgsl` gives materials 24–28 on a vehicle body temperatures. **Buggy crew:** driver and passenger (AK upright between his knees) reclined in the seats, and a gunner standing on the floor behind them in the ring, leaning on a webbing sling: his pelvis and legs are part 0 and his torso, head and arms are part 1 (`up: 1`), so he twists at the waist with the gun (his waist is 5 cm off the yaw axis; past about 120° the twist is more than a body can do). The PKM has no stock (the gunner's chest is where it would be) and rides on a carriage on the ring (part 1); the gun is part 2 and pitches about `BUGGY.gy/gz`, 0.4 m behind the visible yoke, so the yoke and the hands slip a few centimetres at full elevation. **Motorcycle:** parts 1 and 2 are empty: their pivot (`MOTO.tz`, `gy`) lies in the rider, so a rifle in them left the pillion's hands; the pillion is twisted to the right in the infantry's standing aim (`shouldered(yaw)`: butt in the shoulder, cheek weld), firing 40° off the axis past the driver. The cloth shader's worn-patch noise is seeded by the vertex red, which the baked shading varies, so on vehicles (`isG`) the seed is dropped (it showed as mosaic squares). Wheel treads use `b.at(..., 0, a)` (pitch +a) so the local y axis is radial. `tools/vehshots.mjs ... --aim` adds shots with the weapon traversed and laid on the player, `--q therm=1` passes a query.
- **Enemy air (`combat.js`, phase 3):** a pool of `MAXA` = 6 (`G.air`; types in `ATYPE`: 0 FPV, 1 Lancet, 2 Orlan-10), each with its own uniform block (`aObj` in `main.js`) and one of three meshes (`buildDrone`, `buildLancet`, `buildOrlan` in `tank.js`; `airParts` turns the propeller about the long axis). `planAir` (at a wave start) schedules raids on the main axis: an FPV from wave 2, an Orlan from wave 3, a second FPV and a Lancet from wave 4, more in wave 6; `airSpawn(type, bearing)` puts one 1300 m out. **FPV / Lancet:** transit at 28 / 110 m above ground to a rough fix on the tank, then search in a 70 m circle; every 0.4 s within `see` (380 / 750 m) a lock chance `pc × line of sight × (1 − 0.75 canopy) × (1 − 0.5 speed/8) × smoke × range` (smoke near the tank: Lancet 0, FPV × 0.3); a glimpse narrows the search. Locked, they dive with lead (38 / 68 m/s) and hit for 25–40 / 40–55 hull; a miss blows up on the ground (splash, sets off mines). Smoke within 35 m of the tank breaks a dive (Lancet fast, FPV rarely). Battery 160 / 220 s. Toasts at `warn` range (650 / 420 m) and on the dive; the HUD draws red chevrons for the two most pressing (blinking while diving) in `post.wgsl` from `G.thr` (the final-pass uniform grew a fifth vec4, `e`, and later a sixth, `f`, for the drone video look; all post buffers are now 96 bytes). **Orlan:** circles 280 m round a lagging fix on the tank at 180 m, and while it sees the tank (`G.orlan` counts seconds; phase 5 artillery will use it) every enemy `known` ≥ 4. Shot down it falls trailing smoke. **Hits:** the player's rounds (types 0–3) test each step's segment against the air units (`airHit`; radius `ATYPE.r`); an MG round is one hit point (FPV 1, Lancet 2, Orlan 4). Air contacts that have been announced show as red carets on the minimap. Sound: the nearest air unit gets the drone recording, pitched up for FPV / Lancet and down for the Orlan. **One MG control (Space, touch MG, pad ✕):** the coax by default; it switches to the hatch MG3 when the commander's view or the gunner sight is pitched above 0.3 rad (higher than the gun elevates) or an air unit is within ~5° of the crosshair (`G.hmgAuto`); Q and pad R3 force the hatch MG (there is no separate touch button any more). **Hatch MG3:** 20 rounds/s from the commander's mount on the shared 7.62 belt; it fires along the view and converges on the range of an air unit within ±0.05 rad of the sight line (so leading still ranges), else on the ground or building on the sight line, else at 400 m; the commander's view pitch limit is now 1.2 rad (70°; the gunner sight keeps 0.75). **Cope cage:** from wave 3, 40 % of T-72s (`e.cage`, mesh `buildT72(true)`, `eMesh[2]`): the player's FPV charge does 35 % and a bomber grenade on the roof or engine deck 30 % (and no immobilisation).
- **Mines (`combat.js`, phase 2):** a pool of `MAXM` = 48 (`MX MY MZ` position, `MS` state 0 free / 1 buried / 2 surface / 3 falling, `MT` fall time or age, `MA` arming delay, `MR` marked, `MP` snow stamp pending; `G.mines` exposes them). **Fields:** on a wave start from wave 2 (65 %), `planFields` mines one or two road or trail stretches 120–380 m out towards the main axis: `layField` puts 6–9 mines in two staggered rows across both track lanes over ~20 m and registers the field (`FLD`: x, z, radius) so enemies swing round it (`toPt` pushes them out of radius + 14 m; route points inside a field are skipped). A toast reports it. A buried mine stamps a faint scar into the mask (`blast` r 1.3 m, k 0.3: the mask has 0.78 m texels, so anything smaller vanishes), which `terrain.wgsl` shows as a grey, lumpy dug-over patch and a little warmth in the thermal sight. **Rocket strike:** from wave 3 (55 %, 35–80 s into the wave) `strike()` sounds the `whistle` and warns, 4 s later a cassette bursts 75 m over where the tank was and 10 mines fall 18–80 m around it, visibly, onto the surface (marked). **Trigger:** a pressure fuze, the Leopard's footprint (±1.95 × ±3.9 m) moving or pivoting over an armed mine; enemies never set off their own. **Hit:** 15–25 hull, `veh.immob` 4–8 s (the existing immobilised state: no throttle, a quarter of the steering), speed cut, debris, the red `TRACK n s` pill (`#sT`, also for shell track hits) and a repair clank every ~1.2 s. **Countermeasures:** any ground impact sets off mines within `MCLR[type]` m (HE 4.5, HEAT 2.5, VOG 2.5, 125 mm 2, APFSDS 1.5, 30 mm 1, MG 0.8; buried × 0.8), the drone charge 3.5 m. **Marking:** drone cameras (`droneMines`, FPV 250 m / others 450 m, same cone and line of sight as enemy spotting), the crew (buried mines within 30 m in the sight's ±0.45 rad, every 0.5 s), and rocket mines on landing. A marked mine gets a red-flagged picket (`buildMine` in `tank.js`: the mine, then the picket after vertex `nm`), a buried one shows its top, plus an amber cross on the minimap and a red light on the picket in the dark. Surface mines and pickets are `MAXM` copies of one mesh in `mineO` (`main.js`); `C.mineMesh` rewrites one copy (or collapses it) only when a mine changes. Coax MG: it now fires at the sight's aim point (its own parallax and drop correction) whenever the gun is laid within ~8° of it, else along the bore; before, it was parallel to the gun and 0.9 m off at 20 m (the main gun itself does not correct the 0.9 m sight-head parallax at short range).
- **Enemy artillery (`arty.js`, phase 5 part A):** `initArty` (called from `initCombat` with the helpers it needs) exposes `G.arty`. When `max(G.orlan, G.rep)` reaches `WATCH` = 15 s during a wave (`G.state` 1, not `G.peace`, cooldown `cool` over, nothing pending), `call(x, z, src)` schedules a barrage on the point observed at that moment (`G.arty.x/z`, `src` 'orlan' or 'crew'): it is due 20–40 s later (`t`), 4–8 rounds 0.5–1.6 s apart within 25–40 m (`R·rnd^0.75`), plus a ranging round 60–120 m off 4–7 s earlier; the cooldown is due + 60–90 s. Up to `MAXR` = 10 rounds in typed arrays (`rt` time to impact, `rx rz`, `rs` 0 free / 1 scheduled / 2 whistled / 3 in flight, `rk` 1 = ranging). 2.1 s before impact the `incoming` sound plays at the aim point (buffer `inc` in `audio.js`: a swelling falling whistle that stops at the impact); for the last 1.3 s the round is shell type 10 in the combat shell pool (fired from above along the battery bearing at 320 m/s, 55–70° descent, so it shows a short tracer streak and hits terrain, buildings, colliders or the tank on its own). Its impact (`G.arty.boom`) is `explode(…, 4)` (scorch/crater stamp, shake), a column of snow and earth with falling clods, the player hit 45–60 directly or within 2.5 m and 16 → 0 at 2.5–18 m, enemies within 16 m (no score: their own guns), `C.bld.splash` r 14 / 60 and direct building damage `BDMG[10]` = 120, mines within `MCLR[10]` = 7 m. The ranging round's landing toasts 'Artillery ranging on you — move!' when the player is within 300 m; there is no toast when the fire is called. A wave ending drops rounds not yet in the air; `G.restart` calls `reset()`. `G.arty.imp` counts impacts and `ix iz ik` hold the last 32 (for tests). Moving away after the ranging round is the counter (measured: 5–30 hull per barrage standing still, 0 driving off).
- **Driving and aiming:** one momentum physics for the tank (faster on plowed roads than in deep snow, pivot steer, brakes that hold on slopes, suspension squat and recoil rocking). The mouse moves a stabilised sight line; a terrain ray march gives the aim point and range, and the turret and gun slew at their own rates towards the ballistic solution for the loaded round. Cameras: commander view (0), gunner sight (1), drone (4). Mode 3 (free-fly) still exists in `main.js` but has no player control any more (removed as a cheat; the F key and `api.fly` are gone). - **Thermal sight (V: off, white-hot, black-hot; gunner sight and drone only):** when `G.groom.w` is 1 every scene shader returns an apparent temperature through `thermal()` in `common.wgsl` instead of lit colour (snow 0.1, forest 0.2, houses 0.24, hull 0.4, running gear 0.8, engine deck and fire above 1; vehicles have the engine at the rear, local +z). `thermalView` in `post.wgsl` turns that into the display (coarse detector grid, noise, blooming through the bloom chain; green for the tank, grey for the drone). - **Trees (`trees.js`, `tree.wgsl`, `treedeform.wgsl`):** about 207k instances on the high tier, 3 species and 4 LODs (37/180/850 m × `lodMul`), with a two-phase cross-fade. Snow load must look the same on every LOD (see "Lessons"). Per-tree variation lives in `treedeform.wgsl` as a function of the unit-height position and a hash of the trunk position, so every LOD and the shadow passes agree: a lopsided, wavy crown outline, lean, width, a bare lower trunk on big spruces (crown base `cb`; the dead branches below it are not drawn), a darker crown interior (`d.ao`), and the snow load and roughly metre-sized snow clumps, evaluated per vertex (`sv.x`; a fragment-shader noise for the clumps cost 3–5 ms on the GTX 1060). The mid and far spruce and pine models use irregular whorls (`tier(..., jit, js)`). The per-LOD snow extents (`SNOWX`, `?sx=`) were rematched with `tools/lodcmp.sh`, which now works in the real world, has snowfall turned off and needs no ffmpeg (`tools/imgmean.py`). The lodcmp frame mixes LODs (background trees dominate the mean), so read it as a check on background LOD pairs. The menu's Trees setting (`setTreeQ` in `main.js`; `localStorage.gtrees`, `?trees=high|medium|low|off`, `?notrees`) switches at run time. High is the full reference. Medium casts shadows from the mid and far models instead of the 4002-triangle spruce and scales the LOD ranges by 0.8. Low also draws a random half of the farthest trees from a thinned instance buffer (1.32× wider), scales the ranges by 0.55 and drops tree shadows from the far cascade. Off: not drawn or shadowed, not solid, no canopy shade on the snow (`lod2.y`), and no cover for enemy line of sight. Measured in the forest at Frognerseteren (all cascades drawn): 12.8 M tree triangles on high, of which 9.0 M in the shadow passes; about 5.1 M on medium and under 2.8 M on low. The debug overlay prints the live counts (`R.triStat`). On a weak Windows laptop GPU the frame rate was the same on high, medium and low (12–13 fps, 45 with trees off), so there the cost is per pixel (shading, overdraw, MSAA), not per triangle; tree cells are therefore drawn nearest-first, and `?tfs=0` draws trees in a flat colour to separate shading cost from fill cost. That laptop turned out to be rendering on its integrated Intel GPU (`gen-12lp`), not its NVIDIA card: 164 ms GPU time on high with 12 M tree triangles, 130 ms with flat-shaded trees, 37 ms on the low tier with 1.9 M, so it is mostly geometry-bound after all. The overlay and menu now show the adapter (`R.gpuName`), and the automatic tier drops to low on Intel `gen-N` adapters and medium on other Intel `lp` ones. On Windows the browser, not the page, decides which GPU a tab gets (Settings → System → Display → Graphics).

- **Infantry rendering (`soldier.js`, `soldier.wgsl`, `soldiershadow.wgsl`; phase 6A):** the interface with the infantry logic is `G.inf = { n, d }` (created in `initCombat`, `MAXI` = 40): `n` = slots in use (upper bound for iteration), `d` = `Float32Array(MAXI * 8)`, per soldier `[x, y, z, yaw, pose, phase, aim, state]`. `x y z` = feet on the ground, `yaw` as for vehicles (forward = (−sin yaw, 0, −cos yaw)); `pose` 0 stand, 1 walk, 2 run, 3 kneel-aim, 4 prone-aim, 5 stand-aim, 6 dead, 7 RPG-aim (kneeling, RPG-7 on the shoulder, rifle slung; every other pose carries the AK-74); `phase` = animation clock in seconds (dead: seconds since death); `aim` = weapon pitch (rad, up positive); `state` 0 unused, 1 alive, 2 dead (state 2 means dead whatever the pose). The walk/run cycles match `WALK_V` 1.45 m/s (`WALK_HZ` 0.92) and `RUN_V` 3.9 m/s (`RUN_HZ` 1.38): advance `phase` by `dt × speed / WALK_V` (or `RUN_V`) and the planted foot does not slide (measured 0.02 / 0.06 m/s). - **Sound (`audio.js`, `sndrec.js`):** the engines, tracks and drone are recorded loops; everything else is procedural Web Audio. Recorded: six short MP3s (24 kHz mono, 40 kbit/s, about 84 kB, about 110 kB in the bundle) in `src/data/snd/`, cut by `tools/snd/prep.py <source dir>` from Freesound files (sources and authors in `tools/snd/CREDITS.md`; the originals are not in the repo). Each file holds a 0.1 s margin, the loop body L and F seconds of continuation (`meta.json`); `decode()` builds the seamless loop after `decodeAudioData` by cross-fading the start with the continuation, so the seam does not depend on the browser's MP3 decoder delay. `sndrec.js` holds the imports so `audio.js` stays importable in Node. Player engine: three layers at one pitch (`e0` Leopard 2A4 idle, `e1` Leopard running, `e2` a heavier engine with its whine notched out), equal-power cross-faded by load (`ld` from throttle and speed), playback rate 0.85 at idle to about 1.45; tracks `tk` at a rate following speed; enemies a T-26 on the move (`en`, engine and tracks together); drone `dr`, a fly-by resampled to a constant rotor pitch, played twice detuned 2.7 %. Procedural: `synth()` renders 13 mono buffers at load (pure JS, about 0.15 s; `node tools/audio-check.mjs` prints peak/RMS per buffer and fails on NaN or clipping): guns, explosions, hits, reload, smoke, collapse, crash, MG loop and a noise buffer for the snow crunch; the turret whine is two oscillators. The `AudioContext` is created on the first gesture; without one the game runs silent. The tank's voices sum into one bus that is attenuated, low-passed and panned from the camera like any source (so it fades in the drone view); three enemy voices go to the nearest live enemies. One-shots arrive through `C.sfx(name, x, y, z, k)` (`gun egun auto boom hit reload smoke collapse crash whistle atgm mgb incoming`) and play on a pool of 12 chains (lowpass, gain, stereo pan; the quietest is dropped when full) with distance gain, air-absorption lowpass and a `d / 340` s delay (cap 3 s); cannons beyond 300 m use the distant-report buffer. `update(dt)` only sets AudioParams and runs before the `simOnly` return. Master 0.6 through a compressor; M or the menu toggles it (`localStorage.gsnd`), muting also suspends the context. **Sound is on by default**; a stored choice (`localStorage.gsnd`) and `?mute` win. On iOS audio only unlocks on the release of a touch, needs `navigator.audioSession.type = 'playback'` to ignore the silent switch, and can be `interrupted`; that fix is untested on a device.

The dead stay; a slot is recycled only after 20 s and 150 m from the camera. 10 points per soldier, 40 for an RPG or ATGM team (toast). Keyboard and touch are unchanged (no hold). **Drone glide:** `glide()` in `combat.js` gives the velocity a firm rate while the sticks are deflected and a slow one when they are let go (FPV 2.6 / 1.3, bomber 3.2 / 1.4, recon 2 / 1.1 per s; height does not coast: released, it stops at 7/s), so it coasts like a DJI: about v / coast metres (FPV 20 m from 26 m/s, bomber 10 m from 14 m/s). **Drone view levels** (pad D-pad ↑↓ in the drone, mouse wheel, pinch; `D.view`, remembered per type in `G.dview`): FPV 0 chase far (7 m), 1 chase (2.3 m, default), 2 goggles (camera in the nose, bolted to the frame: it rolls with the sideways lean `-D.tr` plus a bank into pad yaw turns, and pitches only with the change of the forward lean `D.tp - D.tpS`, as if the camera were tilted up for cruise; bomber and recon cameras stay gimbal-stabilised); bomber/recon 0 outside (4.5 m behind, 1.8 m up, for landing on the tank), 1 gimbal camera (default), 2 and 3 optical zoom 2× / 4× (`R.dZoom` narrows the field and slows the look). `R.dFirst` hides the drone mesh. **Drone video:** the final pass (`post.wgsl`, `U.f`: x 1 analog goggles / 2 digital, y link quality) bends the FPV goggle picture (wide lens, dark rounded edges), washes out colour, adds scanlines, grain, torn lines and static as the link weakens; the digital (DJI-style) bomber/recon camera breaks into blocks below 55 % and darkens before it drops. Link quality `D.sig` (combat, every 0.25 s): 1 out to 70 % of the radio range, fading to 0 at the limit, × 0.4 with terrain between the tank and the drone (`radioPath`), × 0.75 through a building (smoke and trees do not matter). **OSD** (`#osd`, `U.osd` in `ui.js`, fed from `main.js` in first person only; writes at most every 0.15 s and only changed corners): analog FPV (RSSI, time, battery, km/h, height, home distance with arrow, LOW SIGNAL) and DJI-style (type and zoom, signal bars, battery, time, H, H.S, D with arrow, grenades, WEAK SIGNAL). Not checked on a phone layout yet. Pad yaw is a rate with momentum (`inp.yawR`, `D.yr` in `main.js`: 1.5 rad/s, spin-up 5/s, coast 4/s, about 21° after release); mouse turns stay direct. UI text is English.
- **Game loop:** six waves, resupply and partial repair between waves, then a victory card and endless play. Each wave is a scenario (`planWave` in `combat.js`): wave 1 'Recon in force' from the north, waves 2–5 a shuffled bag of 'Tank platoon with escort', 'BMP raid on the roads', 'Pincer' and 'Two echelons', wave 6 'Final assault'. The main axis changes every wave (picked among bearings that have trails or roads at 500–1000 m, at least about 60° from the last one); groups can arrive later (`PQ` pending spawns, by time or when few are left) and are announced with direction and range. Roles per vehicle (`e.role`): assault (closes to a stand-off range), overwatch (drives to a high spot with a view, `pickSpot`, and holds), flanker (swings wide to the side first), raider (BMP, fast along the plowed roads `W.roads`). All of them shoot and scoot, pop smoke and back off when hit, keep station in a column, slide along walls and escape after repeated stuck events (`G.stuck` counts them). `?peace` (also implied by `auto`, `perf` and the fantasy world) disables the waves. The menu row Peace mode (`#mP`, `api.peace`, `localStorage.gpeace`) does the same at run time: it sets `game.peace`, restarts, and is remembered; the fantasy world is always free roam.

### Performance discipline
- Measure GPU time with timestamp queries, not just frame time. Compare before and after with an **A/B under identical conditions** (stash, build, measure, pop).
- Other apps on the machine (browser, IDE, WindowServer) skew absolute numbers a lot. Report the load you saw, and don't treat a loaded-machine number as the baseline. The idle baseline on high/native was frame avg 14.2 ms / p99 18.3 ms and GPU avg 12.9 ms / p99 15.4 ms. (That baseline is the groomer on an M2 Max.)
- **Who runs what (owner's rule, 2026-11-20):** mechanical runs — the behaviour suites (`lighttest`, `wavetest`, `bridgetest`, ...) and performance measurement (`vehgpu.mjs`, `perf.mjs`, `treegpu.mjs` A/B) — go in a background script from the main session or to a cheaper subagent (Sonnet) that only runs the given commands and reports PASS/FAIL lines, numbers and `uptime`; it does not diagnose or fix. Interpreting a failure (known noise: `roadtest` near its limit, rare `[pageerror] undefined` bursts, `wavetest` stuck counts), diagnosis and judging renders stay on the main model. Subagents that build something run only the one test they need to know the game still works, with a capped number of render rounds (three was enough for the BTR and T-72); the full suite and the perf A/B are run once on the combined build.

## How the work was done (process to keep following)
1. **The first prompt was a full spec**: the world, groomer, grooming mask, controls, quality tiers and DRS, the verification plan and a "done when the critic gate passes" criterion. Write a working `index.html` early, then iterate in milestones (terrain, then trees, then groomer and mask, then lighting and post, then UI and perf). Overwrite `index.html` and commit after each one.
2. **Every visual change is verified with renders**: the fixed poses, drive frames and video where motion matters. Analyse problems quantitatively when possible (mean colour per LOD, frame-time stats) instead of eyeballing.
3. **Follow-up requests from the user are in Norwegian, and you answer in Norwegian.** (The in-game UI stays English.) The pattern is: analyse the root cause with measurements, explain what was wrong, fix it, verify with renders and perf, commit, and report briefly with honest caveats (what wasn't verified, and measurement noise).
4. **Examples of follow-ups:**
   - The tree LOD "pop" (heavy snow at a distance, little up close) was fixed with consistent snow extent on all LODs, shading for the far LODs, and a two-phase cross-fade.
   - Turbo mode (driving fast, drifting and jumping) added kickers on the lake and ballistic physics. It was removed again when the groomer became a tank; only the ballistic crest physics survives.
   - The tank conversion: Leopard model, driving and fire control, weapons and effects, Russian enemies with AI, waves and HUD, in that order, one commit per milestone.
   - Real Nordmarka (phase 1): map data pipeline, real terrain, lakes, trails, houses and landmarks, then a start screen to choose between the real world (two start points) and the fantasy world. Phase 2 (not started) is streaming trees and a larger world north to Kikut.
5. When a usage limit interrupts the work, resume where it stopped without redoing finished work.

## Lessons / gotchas
- WebGPU doesn't allow `alphaToCoverageEnabled` together with a `sample_mask` fragment output. Use alpha cross-fades with alpha-to-coverage instead.
- Blanket renames in WGSL can corrupt identifiers (for example `duv.x` became `dux`). Grep after any mechanical edit.
- Tree LODs have to match in mean colour and snow distribution. Simple cones with full snow cover read as white blobs and pop when they switch. Check with `tools/lodcmp.sh`.
- Wide LOD fade bands and extra skirt geometry cost about 35% GPU time. Keep the band at about 7%.
- A vehicle hit box is thin where hull and turret meet; main-gun shells are sub-stepped every 0.6 m (MG 1.5 m). Coarser steps let rounds pass through the roofline.
- The sight ray ranges on a generous sphere around each enemy (`aimHit`), so a displayed range does not mean the round will hit; scripted tests should aim with `__aimAt` at a point inside the hull.
- Work queued for the renderer during logic-only steps (`__sim`) must survive until a frame is drawn: `blastN` is cleared by the renderer, not by `update`.
- First run on an NVIDIA card (D3D12) showed a line of flickering black and white single pixels with bloom halos in the snow. Suspected cause: the clipmap rings met on an exact shared edge on one side, and rounding opened pixel cracks to the background. The rings now overlap by a cell on every side (`mkIdx`), and `post.wgsl` clamps HDR values so a NaN or inf pixel cannot flash. The overlap did not cure it: with the clamp the pixels are black without halos, and they are reported to sit at the same screen positions however the view is turned, on NVIDIA only (fine on Intel, Apple and software WebGPU). Particles, glow sprites, lamps and the vehicle, drone and tree meshes were scanned and hold no non-finite values. `?hide=` (t terrain, s sky, p particles, v vehicles, o props, h shadow casters, x sight overlay) leaves parts of the frame out to bisect it on the card. Bisecting showed the line survived hiding any single part, stayed put when only the hull turned and moved with the camera: it comes from `skyBase` (used by `applyFog` on every surface), where `pow(az, 3.0)` got a base a rounding error below zero for view directions exactly opposite the sun's azimuth. `pow` of a negative base is NaN in HLSL; other backends return 0. Clamp the base of every `pow`.
- Never append a `//` comment in the middle of a one-line statement chain (this also holds for Python and for JS inside a test's template string, which `commentlint` does not see; the bridge work hit all three): it silently swallows the statements after it (this removed the whole road mask once, and bit the drone, mine and tree work repeatedly). `build.mjs` now runs `tools/commentlint.mjs` first and stops on a trailing comment that looks like it hides code.
- Object materials all have some specular, so a "black" surface in direct sun renders mid-grey. Use `MAT.void` for openings that must stay dark.
- Props that sit on the ground get darkened by the `hAbove` contact term per height texel, which shows as a 2 m staircase on large flat faces; flat snow faces (`MAT.snow`, facing up) skip it.
- `tools/scenes.mjs` indexes into `trails[0]`; an index past the trail length gives NaN and a black frame that also poisons the following scenes.
- Lake material (`mat` R) also blocks tree placement (`> 8`), so terrain edits on lakes have to keep R ≥ 9.
- The grooming mask covers `W.MW` metres (3200 real, 2048 fantasy) at 4096 texels; `stamp.wgsl` has the half-size as the literal `1600.0`, which `main.js` replaces per world. The far-terrain height (`262.0` in `terrain.wgsl`) and far ground plane (`255.0` in `sky.wgsl`) are replaced the same way for the real world.
- Building vertices are edited in place in the CPU copy of the props mesh: always restore the pristine range before applying a state, and keep any per-vertex noise a function of position only, or shared box corners of different faces move apart and crack. Rubble built by squashing the original mesh read as a flat plate (a wall box or roof quad has only its corner vertices to move), hence the separate debris boxes.
- Trees do not stop projectiles; enemy line of sight uses the canopy raster (`nrm` B), which does not change when a tree goes over. Enemy vehicles leave no tracks in the mask.
- **Trees and vehicles (`treeHit` in `main.js`, shared by the player and the enemies via `C.treeHit`):** a vehicle is a capsule (centre, forward, half-length, radius). Trees under `SMALL_T` = 7 m that the hull overlaps while it moves are knocked over: `fell()` aims the instance's rotation along the path and animates the fraction of its species field (`i1.y`, 0.004 → 0.4 over 0.7 s, one 4-byte `writeBuffer` per falling tree), which `treedeform.wgsl` turns into a tip-over about the base (lifted a little so the crown sits on the snow); a snow puff and a crack. Each vehicle has its own height limit (`treeHit(..., small)`): the Leopard 10 m; `ETYPE.fell` T-72 10, BMP 9, BTR 8, Tigr 6, buggy 4, bike 3. An enemy pressing against a big tree (`e.tcT`) fells trees up to 16 m after 1.5 s and anything after 3 s if heavy (`fell` ≥ 8), while a light one then squeezes through; the same after its first / second stuck event. Measured with `wavetest --waves 6`: about 6–10 stuck events per run against 3–4 before (2–3 with trees off), all resolved by the reverse/sidestep logic (0 problems); fewer would need real path finding round the forest. Bigger trees are solid: the vehicle is pushed out and slides along (enemies get a wall contact normal, like buildings); enemies also steer away from big trunks just ahead (`e.tax/taz`), run 35 % slower in full canopy (wheeled 55 %), and their overwatch, scoot and escape spots avoid dense forest (`okSpot`, canopy < 110/255). A restart stands the felled trees up again (`treesRestore`, up to 4096 remembered; past that a small tree stays solid; falls in progress use a ring of 64; a cell with a felled tree gets its culling bounds padded by the tree's length so a crown fallen over the edge is still drawn). Trees off: none of this. The thinned far-LOD copy on the low tier does not show felled trees (they are far away). `tools/treetest.mjs` checks it.
- The real world's tree count is capped (`cap` in `world.js`). If the cap is hit, the southern rows silently get no trees; check `__info()` (about 362k on high).
- Spotlight indexing (`mds`) and other apps can push GPU times to 100+ ms. Check `uptime` before trusting a perf number.
- The mp4 height has to be even for ffmpeg (`-vf scale=1728:1116`).
- Lidar gotchas: a cable along the axis of Holmenkollbakken reads as 10–30 m of 'structure' on the centre line of the landing hill (measure the hill off-axis or from the DTM); under a removed bridge deck (the two ski bridges over Holmenkollveien, the road and rail bridges) the DTM holds a smooth interpolated fill across the hole, neither the road below nor earth: take the lower level from a grade fitted outside both ends, and the deck from the DOM (`tools/geo/bridges.py`); OSM outlines of stands and jump parts arrive as building rectangles (flag 8 in `bldh`). Subagents working in the same checkout can leave the build broken for a minute: a page that will not load right after a build may be someone else's half-made edit.
- `genWorld` in `world.js` is close to the size where V8 stops optimising a function: after the arena and border code were added inline, every loop in it ran about twice as slow and loading went from 4 to 8–12 s, with no single hot line in the profile. Keep new world-generation steps in module-level functions (`edgeBlur`, `inJump`, `inArena`) and check the load time (`ready` in about 4.5 s on the Linux machine) after adding to it.
- Other sessions' dev servers may already hold ports near 8080–8095; a `python3 -m http.server` that cannot bind fails silently in the background, and the tools then talk to someone else's checkout. Check with `lsof -iTCP:<port>` and `readlink /proc/<pid>/cwd`.
- `object.wgsl` reads the ground height under a fragment bilinearly (for the contact term, `terrainShadow` and lamp light). With the nearest 2 m texel, surfaces lying just above a slope (stand treads) showed light and dark 2 m squares that looked like faceted geometry; no measurable GPU cost on the GTX 1060.
- Building rectangles: `house()` draws with `at(-B.yaw)`, so a building's local x axis is (cos yaw, sin yaw) in world x, z, and world -> building is `u = dx cos + dz sin`, `v = -dx sin + dz cos`. `tools/geo/buildings.py` had it right; `compare.py`, `canopy.py` and the tree / road / rail masks in `world.js` had the mirrored angle (found in review: 191 tree trunks inside rotated houses, 0 after). Check against the lidar when in doubt: for elongated rotated buildings the right convention covers 0.86 of the roof, the mirrored one 0.65.
- Anything that moves must test bridge slabs with `W.br.seg` on its movement segment before using `groundAt`: `groundAt` accepts a querier up to `STEP` below a deck top, so a slow riser under a deck would otherwise be lifted onto it (player drone), and a fast diver passes through (enemy FPV / Lancet).
- Unexplained and rare (about 2 of 18 test runs on the Linux machine, in `airtest` and `bridgetest`): a burst of a few hundred `[pageerror] undefined` during a run, i.e. something throws or rejects with no value once per frame for some seconds, after which the run's checks still pass. Re-runs are clean. No `throw` or bare `reject()` exists in `src/`; not reproduced on demand, cause unknown (several headed Chrome instances were running at the time).
- **Playable area:** a box, not a square, in the real world: `W.PB` = [-1850, -1560, 1560, 1750] (x0, z0, x1, z1), with `W.inP(x, z, margin)`, `W.cpx`, `W.cpz` (from `playBox` in `math.js`; the fantasy world gets its square). It was widened west and south so the whole metro line Holmenkollen – Frognerseteren (Skogen at x -1815, Holmenkollen station at z 1670) is inside; the window is still ±2048, so only about 200 m (west) and 300 m (south) remain to the edge there, against 490 m north and east. `W.PLAY` (1560) is kept as the old square for the tests that stage on the lake. The snow mask `MW` went from 3200 to 3712 m (0.91 m per texel instead of 0.78) to cover the box. The big map is centred on the box. Beyond the window the real world's ground is rolling hills shaded as snow-laden forest (`terrain.wgsl`, only where `ROADS` is 1 and outside ±`G.world.x`), because the bare white plain was plainly visible from the new west border. The alpine slope north of the tower lies partly outside the window and needs a larger world.
- `tools/roadtest.mjs` is not stable from run to run on the same build: its last check (wheeled vehicles driving through forest off route, limit 5 %) gave 2.7 and 5.3 on the same commit within minutes (2026-11-19). Treat a single failure near the limit as noise and repeat it.
